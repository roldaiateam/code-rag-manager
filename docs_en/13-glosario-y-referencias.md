# 13 · Glossary and references

## Glossary

**Adapter** — In hexagonal architecture, the concrete implementation of a port (e.g. `LanceDbVectorStore` implements the `VectorStore` port). It lives outside the domain and knows about external libraries.

**AST (Abstract Syntax Tree)** — Structured representation of source code produced by a parser, where each node is a language construct (function, class, call...).

**Chunk** — The smallest unit into which code (or text) is split for indexing; ideally it respects syntactic boundaries (function, class) rather than cutting at a fixed size. See chapter 02.

**Chunking** — The process of splitting a document or repository into chunks.

**Cosine similarity** — A measure of closeness between two vectors based on the angle between them; it ranges from -1 (opposite) to 1 (same direction). It's the typical metric for comparing embeddings.

**Domain** — In hexagonal architecture, the core of rules and entities specific to the problem, with no dependencies on external infrastructure.

**Embedding** — Numeric vector that represents the meaning of a text, generated by a model trained for that purpose. Texts with similar meaning produce nearby vectors.

**Dependency graph** — A structure of nodes (chunks) and edges (relationships: implements, extends, calls, imports) extracted from the code, which allows answering structural navigation questions.

**Hexagonal (architecture) / Ports & adapters** — A pattern that separates the domain from infrastructure through interfaces (ports) implemented by interchangeable adapters. See chapter 03.

**Incremental indexing** — Reindexing only what changed since last time (typically via `git diff`), instead of reprocessing the whole repository. See chapter 07.

**JSON-RPC 2.0** — Message format used by MCP: requests and responses as JSON objects with `method`/`params`/`id` and `result`/`error`.

**k-NN / ANN (k-nearest neighbors / approximate nearest neighbors)** — The problem a vector store solves: finding the k vectors closest to a given one. "Approximate" because, at scale, some exact precision is traded off for speed.

**MCP (Model Context Protocol)** — Open protocol for an LLM agent to discover and use external tools in a standardized way, regardless of the client (Claude Code, Codex CLI, Copilot CLI...). See chapter 08.

**Port** — In hexagonal architecture, an interface that the domain/application needs, without specifying how it's implemented. See chapter 03.

**RAG (Retrieval-Augmented Generation)** — A technique that combines retrieval of relevant information with text generation by an LLM, instead of relying only on what the model "remembers" from its training. See chapter 01.

**Recall@k** — Retrieval quality metric: of all the results truly relevant to a query, what fraction appears among the first k results returned.

**Hybrid retrieval** — Combination of semantic search (embeddings), lexical search (text/keyword matching), and, in the case of code, structural search (dependency graph) to improve on any of the three alone. See chapter 02.

**Stdio (transport)** — Communication method for a local MCP server: the client writes requests to the standard input of the server process and reads responses from its standard output. Requires no network or ports.

**Token** — The smallest unit of text a language model processes (roughly a word or word fragment). Relevant to an LLM's context limit and, with some providers, to the cost of generating embeddings (billed per token).

**Tool (in MCP)** — A function exposed by an MCP server, with a name, description, and `inputSchema`, which an LLM client can decide to invoke based on its description.

**Top-k** — The number of results a search returns (e.g. "the 10 most relevant chunks").

**tree-sitter** — Incremental parser generator with grammars for multiple languages, used to produce the AST from which chunks are extracted. See chapter 05.

**Vector store** — A store specialized in holding vectors (embeddings) along with their metadata and efficiently answering similarity queries (k-NN/ANN). See chapter 06.

## References for further reading

Since this is a fast-moving field (embedding models, MCP SDKs, client configuration formats), always prioritize the current official documentation over what's written here if you spot a discrepancy:

- **MCP specification**: the official Model Context Protocol site (`modelcontextprotocol.io`) — the source of truth for the protocol itself, independent of any specific client.
- **Claude Code documentation on MCP**: the MCP section in the official Claude Code documentation (`code.claude.com/docs`).
- **Codex CLI documentation on MCP**: the extensibility/MCP section in the official Codex documentation (under `developers.openai.com` / `learn.chatgpt.com`, depending on how the documentation is organized at the time of consultation).
- **GitHub Copilot CLI documentation on MCP**: the "Adding MCP servers" section at `docs.github.com`, under Copilot CLI.
- **tree-sitter**: official documentation for the project and its Python bindings (`tree-sitter`, plus the per-language grammar packages, e.g. `tree-sitter-python`).
- **LanceDB / ChromaDB**: official documentation for each project for the concrete API for creating tables/collections and searching.
