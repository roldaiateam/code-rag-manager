# US-11 — Real BM25 lexical index

**Tier:** Nivel 2 · **Depends on:** US-04
**Design reference:** `PLAN-MEJORA-CODE-RAG-MANAGER.md §2.3` (theory), §7.1, §12 point 6

## Story

As an agent searching for a rare, specific term, I want the lexical channel
to weigh rare terms more heavily than common ones and to not let long chunks
win just by being long, so that lexical retrieval matures beyond fixed
per-field point weights (US-01/US-05) into statistically grounded scoring.

## Priority note

This story fixes the same "trampa"-category root cause as US-01, more
rigorously (statistically grounded scoring vs. fixed per-field point
weights). US-01 is the cheap stopgap; this is the real fix. If lexical
retrieval quality stays a priority after US-01 lands, consider fast-tracking
this story — and its US-04 dependency — ahead of the rest of Nivel 1, rather
than leaving it queued behind the classification work as a distant Nivel 2
item.

## Context

`LexicalIndex` port (`index(project_id, chunks)`, `search(project_id, text,
top_k)`) already has the right shape — this is a pure adapter swap, no
domain/application/port changes. **Decision: hand-rolled implementation, no
new dependency** (neither `rank-bm25` nor `bm25s`) — see design doc §12
point 6 for the reasoning (corpus scale doesn't need it; consistent with the
project's existing "no dependency when scale doesn't demand it" pattern).

## Acceptance criteria

- [ ] `domain/bm25.py`: pure BM25 formula
      (`score(d,q) = IDF(q)·f(q,d)·(k1+1) / (f(q,d)+k1·(1−b+b·|d|/avgdl))`),
      `k1=1.5`, `b=0.75` as starting constants, testable with hand-fed
      term-frequency/document-length numbers, no real index required.
- [ ] New adapter `adapters/storage/bm25_lexical_index.py` implementing
      `LexicalIndex`, replacing (or offered alongside, behind config)
      `SubstringLexicalIndex`/its multi-field successor (US-05).
- [ ] Tokenization for both indexing and querying goes through
      `domain/tokenizer.py` (US-04) — same normalization on both sides, but
      **not symmetric in when or in synonym expansion** (see US-04's "where
      and when this runs"): every chunk's fields are tokenized via
      `tokenize()` once, when the inverted index is built (mandatory here —
      IDF needs corpus-wide term statistics before anything can be scored);
      the query is tokenized and **synonym-expanded** via `expand_query()`
      fresh on every call, then each resulting term is looked up against the
      already-built index/statistics. Synonyms are never baked into the
      indexed side, so an `extra_synonyms` change takes effect on the next
      query without forcing a reindex.
- [ ] **No dedicated persistence file for the inverted index.** It is
      rebuilt in memory on every MCP server startup / CLI invocation, from
      the chunks (`source_text`) already persisted by `VectorStore` — same
      "rebuildable cache" philosophy already stated in `README.md` for the
      rest of `.crm/`.
- [ ] Unit tests: rare term scores higher than a common term appearing the
      same number of times; a long chunk repeating a term doesn't
      out-score a short, precise match without bound (saturation + length
      normalization both verified with constructed examples).

## Out of scope

- Incremental statistics updates between reindexes — not applicable, `crm`
  always does a full rebuild (see design doc §8/§9's decision against
  incremental reindexing).
- Switching to `rank-bm25` — noted as an explicit escape hatch in the design
  doc if corpus scale ever demands it, not part of this story.
